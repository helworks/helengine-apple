# HelEngine Apple

Shared C++20/Objective-C++ backend for macOS and iOS using SDL3 and Metal. Source checkout: `C:\dev\helworks\helengine-apple`; approved native checkout: `/Users/distro/dev/helworks/helengine-apple`. Work is on the real `main` checkout, with no worktrees or source exports.

The native diagnostic currently builds on Apple Silicon with Xcode 26.2. Actual Metal tests on Apple M2 verify texture upload, ordered alpha blending, GPU completion/resource retention, scissor clipping and per-corner rounded borders through offscreen pixel readback. Lifecycle tests cover suspension, zero-sized viewports and unavailable drawable pacing. macOS Debug and Release have passed; iOS device and simulator Debug have compiled unsigned against SDK 26.2. Unsigned compilation does not prove device deployment or execution.

The authored shader contributor compiles HLSL using the engine's shaderc frontend as an intermediate compiler, then translates SPIR-V to MSL with SPIRV-Cross and builds a real Metal library with the selected Apple SDK. Metal remains the only Apple runtime renderer. Material cooking preserves the engine binary format, authored resources and fixed float32 GPU constant layouts. Target registration uses two thin assemblies sharing `helengine.apple.builder` so the existing assembly-only loader selects one unambiguous target per assembly.

The iOS Metal graphics profile exposes `screen-orientation`: `unspecified` retains automatic rotation, `portrait` supports the portrait family, and `landscape` supports both landscape sides. Existing projects default to `unspecified`. This explicit choice configures both the packaged `UISupportedInterfaceOrientations` and SDL's view-controller orientation mask; window width and height do not imply an orientation. For a landscape game, set `graphics.selectedOptionValues.screen-orientation` to `landscape` in its iOS platform settings. The mappings can be checked with `cmake -P tests/ios_orientation_test.cmake` in addition to the managed builder checks.

The real generated macOS Core and DemoDisc gameplay execute the complete 15-scene catalog. Apple M2 Debug and Release 32/32 offscreen validation passed all 14 rendering scenes, using hardware indexed visibility for the ten GPU scenes and 1,200 real update/draw frames for each CPU path tracer. All four tracers completed one sample per pixel with zero non-finite samples. The startup menu passed 300 frames with 321 draw calls, all 44 unique authored item IDs, keyboard edges and real SDL virtual-controller navigation. All fourteen catalog-launched rendering scenes also returned to the full menu through keyboard Escape and SDL virtual-controller East input: 28/28 paths, with ten real scene draws before the press and 120 captured frames per run. Only the authored gameplay requested each return transition. No scene buttons were filtered. These checks establish actual rendering and lifecycle behavior; they do not certify visual parity or performance.

The native 3D provider consumes authored indexed submeshes, shader reflection, material constants/textures, forward lights, shadow atlas and point shadow cubes. Controlled Core draws with simulation held fixed verify that disabling shadows changes receiver pixels in both authored shadow scenes and re-enabling them exactly restores the image. GPU fixtures verify projected/radial shadow depth, cube faces, matrix packing, material pixels and counterclockwise front-face culling. Project-specific assertions remain in tests; production startup consumes the shared manifests.

The iOS player uses SDL callbacks, portable touch/gamepad snapshots and lifecycle pacing with the same Core/Metal providers. Actual generated Core device and arm64 simulator unsigned linking passed against SDK 26.2, preserving canonical generated Core/package inputs across SDK changes. The complete current-vendor CLI pipeline also cooked and staged all 15 scenes for both SDKs; inspection verified ten authored MTLB libraries with the expected SDK provenance and no opposite-SDK markers in each package. The single final package is the simulator bundle at `/tmp/helengine/ios/package/helengine_ios.app`. No physical-device or simulator execution is claimed. macOS Profiler now builds optimized code with symbols, the pinned Tracy transport, generated CPU stage/component/entity samples and profile-specific generated-scope defaults. Its adapter test and actual 400-frame menu capture passed with 63,693 generated CPU events across 83 functions, five component plots and four entity plots. The capture is CPU-only; GPU timestamps are not validated. iOS Profiler still fails explicitly until its runtime capture is verified. Resource arrays, deferred/HDR/normal-map rendering, multiple queued 3D cameras and authored render targets remain explicitly unsupported. The full generated Core validation baselines are Debug and Release 32/32; other numeric policies remain unverified.

CMake and SDL archives are SHA-256 checked; compiler source commits and their transitive DEPS are fixed. The engine SDK is .NET 9.0.308 with roll-forward disabled.

```sh
python3 /Users/distro/dev/helworks/helengine-apple/scripts/build_native.py --target macos --profile Debug --diagnostic
python3 /Users/distro/dev/helworks/helengine-apple/scripts/build_native.py --target macos --profile Release --diagnostic
python3 /Users/distro/dev/helworks/helengine-apple/scripts/build_native.py --target ios --profile Debug --sdk device --diagnostic

```
